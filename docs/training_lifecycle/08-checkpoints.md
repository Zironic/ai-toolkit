# 08 — Checkpoint Saving & Metadata ✅

TL;DR
- Checkpoints are saved by `BaseSDTrainProcess.save()` (called periodically by the training loop, at the end of training, and when `save_before_stop` is triggered). The system supports `safetensors` and `diffusers` formats, saves per-step artifacts (model, LoRA, adapters, embeddings, optimizer), writes rich metadata via `toolkit/metadata.py` (`get_meta_for_safetensors`, `add_model_hash_to_meta`), and enforces retention via `save_config.max_step_saves_to_keep`. Optionally, completed runs can be pushed to Hugging Face Hub using `push_to_hub()`.

Files & symbols referenced
- `jobs/process/BaseSDTrainProcess.py` — `save()`, `clean_up_saves()`, `push_to_hub()`, `get_latest_save_path()` (see lines ~860–1040 and ~3140–3187)
- `toolkit/saving.py` — helpers to save LDM/LoRA/adapter state and conversion utilities, `save_file()` wrappers (safetensors usage)
- `toolkit/metadata.py` — `get_meta_for_safetensors()`, `add_model_hash_to_meta()` for metadata enrichment and legacy hashes
- `toolkit/config_modules.py` — `SaveConfig` keys: `save_every`, `dtype`, `max_step_saves_to_keep`, `save_format`, `push_to_hub`, `hf_repo_id`, `hf_private` (lines ~1–60)

When & how checkpoints are saved
- When triggered:
  - Periodic saves: `is_save_step = (self.save_config.save_every and self.step_num % self.save_config.save_every == 0)` (triggered in `run()` loop).
  - End-of-training: `save()` is called once at the end (if `accelerator.is_main_process`).
  - Save-before-stop: `maybe_stop()` checks `save_before_stop` and triggers `save()` before stopping.
  - Manual saves: some process implementations call `save()` in their own `save()` hook.

- Save format & naming:
  - Default filename: `{job.name}_{zero_padded_step}.safetensors` (zero-padded 9 digits) or `{job.name}.safetensors` for step-less saves.
  - LoRA and embeddings have special naming (e.g., `{job.name}_LoRA_{step}.safetensors` or `{embed_trigger}_{step}.safetensors`). Adapter saves may be diffusers folders (`.save_pretrained()` behavior) with `aitk_meta.yaml` written next to them; control_net adapters may be saved in diffusers format.
  - Save formats: `safetensors` (default) and `diffusers` (folder format) as set by `SaveConfig.save_format`.

Metadata & hashing
- Metadata building occurs via `get_meta_for_safetensors(meta, name)` in `toolkit/metadata.py` which stringifies nested objects and injects `software` info. This metadata is included in safetensors file headers (one-level deep key-values only).
- `add_model_hash_to_meta()` prepares model hashes compatible with sd-webui-additional-networks (adds `sshs_model_hash` and `sshs_legacy_hash` keys by hashing the saved safetensors bytes) to accelerate downstream indexing.
- Additional save metadata can be provided by adapters or embedding components (e.g., `adapter.get_additional_save_metadata()`), which is merged into the global `meta` before saving.

Artifacts saved
- Model: `self.sd.save(...)` writes model weights (or `self.sd.save_refiner(...)` for refiner) in the chosen `save_format`.
- Network/LoRA weights: saved via `network.save_weights(file_path, dtype, metadata)` when Network is present.
- Embeddings: saved via `self.embedding.save(...)` (format controlled by EmbeddingConfig.save_format).
- Adapter/ControlNet: adapter-specific logic uses `save_ip_adapter_from_diffusers()` (safetensors) or `adapter.save_pretrained(...)` (diffusers), writes `aitk_meta.yaml` for folder-based adapters.
- Optimizer: `optimizer.pt` is saved via `torch.save()` in `save_root` (best-effort wrapped in try/except).
- Auxiliary: `learnable_snr.json` for learnable SNR parameters if present; dataset evaluation JSON if `train_config.save_loss_json` is set.

Retention & cleanup
- `clean_up_saves()` enforces `save_config.max_step_saves_to_keep` by listing files matching the job naming pattern and removing older files (applies to safetensors, `.pt`, directories/adapter folders, and embedding files). Certain model-specific multipliers (`sd.max_step_saves_to_keep_multiplier`) may adjust retention counts.
- After saving, `clean_up_saves()` removes the older items and returns path of latest item.

Push-to-hub behavior
- If `save_config.push_to_hub` is true, at the end of training `BaseSDTrainProcess.push_to_hub(repo_id, private)` will:
  - Write a `README.md` with metadata generated by `_generate_readme()` and create or reuse an HF repo using `HfApi.create_repo()`.
  - Upload the folder with `api.upload_folder(..., ignore_patterns=["*.yaml","*.pt"])` to avoid pushing private files.
- If `HF_TOKEN` is not in env, the code calls `interpreter_login()` to capture credentials interactively.

Restore & discovery
- `get_latest_save_path(name=None, post='')` searches `save_root` for most recent matching safetensors, `.pt` or directories, excluding LoRA/refiner/t2i/cn by default, and returns the most recent path as a resume candidate.
- For LoRA-pretrained paths, if no checkpoint is found locally it will use `network_config.pretrained_lora_path` if present and exists on disk.

Observability & tests recommended
- Check correctness of saved files: iterate keys in `safetensors.safe_open` and validate presence of expected parameter keys and `metadata` content (use `load_file` or `safe_open`).
- Test that `add_model_hash_to_meta()` produces consistent hashes for deterministic state dict bytes (use in-memory save via `safetensors.torch.save` + `BytesIO`).
- Test retention: save more than `max_step_saves_to_keep` and assert older files are deleted while newest remain.
- Test push-to-hub: mock `HfApi` to assert `create_repo()` and `upload_folder()` are called with expected args and that README.md contains required metadata.

Files read (manifest)
- `jobs/process/BaseSDTrainProcess.py` (save(), clean_up_saves(), push_to_hub())
- `toolkit/saving.py` (conversion & safetensors helpers)
- `toolkit/metadata.py` (get_meta_for_safetensors, add_model_hash_to_meta)

Notes & uncertainties
- Adapter saving behavior is intentionally varied: control net adapters are saved in folder/`diffusers` format while other adapters are saved as safetensors — tests should cover both code paths.
- Push-to-hub flow may require user interaction for login when `HF_TOKEN` is missing — consider documenting a CI-friendly non-interactive path for automation.
